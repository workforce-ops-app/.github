# 0033. Node.js 24 LTS for frontend tooling

- **Status:** Accepted
- **Date:** 2026-09-30
- **Supersedes:** the Node.js line of [0010](0010-runtime-versions.md)

## In short
The frontend's development tools (formatting, linting, tests) run on Node.js 24, the current long-term support release, instead of Node.js 22. The switch is made now, before any frontend code exists, because now it costs almost nothing.

## Context
[0010](0010-runtime-versions.md) chose Node.js 22 LTS. Since then Node.js 24 became the active long-term support release, supported until April 2028, while Node.js 22 receives security fixes only, until April 2027. Node.js runs only development tools in this project; the application itself is served as static files by nginx ([0005](0005-frontend-multi-page-vanilla-js.md)). No `package.json` or lockfile exists yet, so nothing has to be migrated.

## Decision
- Node.js **24 LTS** for frontend tooling, locally and in CI.
- CI installs Node.js 24 (`node-version: "24"` in the shared workflow).
- When the frontend skeleton adds `package.json`, the same pull request pins the version: an `.nvmrc` with `24`, an `engines` entry for Node.js 24, and a Dependabot rule keeping `@types/node` on 24, the way Python and MySQL are pinned.
- Python 3.13 and MySQL 8.4 LTS from 0010 are unchanged.

## Consequences
- Both teammates install Node.js 24 (`node --version` shows `v24.x`); the setup guide and setup issues say so.
- Supported beyond the end of the project's semester, so no upgrade is expected during the project.
- Using the same major version everywhere avoids lockfile churn between npm versions.

## Alternatives considered
- **Stay on Node.js 22:** supported through the semester and already in CI, but already in maintenance, and a later switch would mean regenerating the lockfile and re-checking every tool.
- **Always the newest Node.js release:** non-LTS releases have short support and more breakage.
